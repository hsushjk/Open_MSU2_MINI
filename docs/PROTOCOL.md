# MSU2_MINI 通信协议（V1.1 官方固件实测整理）

协议由两条独立线索交叉验证得出：

1. 官方上位机 `MSU2_MINI_Console`（Python，`MiniProtocol` / `FrameEncoder` / `MiniDevice`）的发送侧实现；
2. 反编译固件 `cmd_dispatch`（0x250）与 `main_loop`（0x59A）的接收侧实现。

两侧完全对得上，因此本文件可作为**独立实现该协议的规范**。

---

## 1. 物理层

| 项目 | 说明 |
|---|---|
| 设备类型 | USB 2.0 全速，复合设备：CDC-ACM（虚拟串口）+ HID |
| 接口 0 | CDC-ACM 控制接口，EP 0x81 中断，64 B / 1 ms |
| 接口 1 | CDC 数据接口，EP 0x02 Bulk OUT（主机→设备）、EP 0x83 Bulk IN（设备→主机） |
| 接口 2 | HID，64 B 输入 + 64 B 输出报告；EP 0x04 中断 OUT、EP 0x84 中断 IN |
| 波特率 | 标称 19200 8N1 —— **对 CDC 无实际意义**，仅为沿用串口 API |
| 设备描述符 | VID `0x1A86` / PID `0xFE0C`（WCH 示例值，厂商字符串仍是 `wch.cn` / `CH32x035` / `0123456789`） |
| 控制传输 | 支持；HID 的 `SET_REPORT` 会被固件当作命令处理（见 §6 安全提示） |

设备的所有"命令"最终都走同一个 6 字节帧格式，CDC 与 HID 两条通道语义相同。

## 2. 帧格式

**固定 6 字节，无长度、无序号、无校验、无转义。**

```
byte 0 : class   命令大类
byte 1 : sub     子命令 / 操作码
byte 2 : p2
byte 3 : p3
byte 4 : p4
byte 5 : p5
```

- 多字节量一律**大端**（`(p2<<8)|p3`）。
- 颜色为 RGB565 **大端**。
- 固件不校验长度，也不做任何范围检查。

## 3. 握手与会话

上电后设备主动发送 6 字节：

```
00 4D 53 4E 30 31     →  class 0, 'M' 'S' 'N' '0' '1'   （固件内 flash 0x5E90 的 "MSN01"）
```

主机必须回复：

```
00 4D 53 4E 43 4E     →  class 0, 'M' 'S' 'N' 'C' 'N'
```

设备收到后把内部状态 `g_main_state` 从 0 切到 1，进入**流式刷屏态**，并原样回显 6 字节。此后所有 LCD 命令才按预期工作。

> 这个握手本质上是"版本打招呼"：`MSN01` 表示 V1.1 官方固件。后续自研固件可改为 `MSN02` + 特性位，同时保持对 `MSNCN` 的兼容处理。

超时：设备侧由 TIM3 生成 1 kHz tick，**5 秒**内没有收到新帧就调用 `reset_session`（清状态机、清队列指针、清 tick），相当于自动断开。

## 4. 命令族

### class 0x00 —— 系统 / SFR

| sub | 参数 | 行为 |
|---|---|---|
| `0x4D` ('M') | `p2..p5` = `53 4E 43 4E` | 握手应答（见 §3），原样回显 |
| `0x30` | `p2 >> 5` = 子操作 | 子操作 0：查表；1：设滤波系数 `k = p3 << 1`；4：向 `0x20000140 + addr` 写 SRAM（**无边界检查**）；5：空操作 |

### class 0x02 —— LCD

| sub | 名称 | 参数 |
|---:|---|---|
| `0x00` | 设置坐标 | `x = (p2<<8)|p3`，`y = (p4<<8)|p5` |
| `0x01` | 设置尺寸 | `w = (p2<<8)|p3`，`h = (p4<<8)|p5` |
| `0x02` | 设置颜色/页 | `p2..p5` 4 字节，写入画图参数块 |
| `0x03` | 绘图操作 | `p2` = 操作码，`p3..p5` 为参数，见下表 |
| `0x04` | 设置填充单元 | `p2..p5` = 4 字节"最常见像素单元"，刷屏时先作为背景填充 |

`0x03` 的操作码（`p2`）：

| 操作码 | 主机用法 | 固件语义 |
|---:|---|---|
| `0x07` | `DRAW_LOAD_ADDR`：`[02 03 07 00 00 00]` | 装载绘图地址/进入直写模式 |
| `0x08` | `DRAW_DATA`：`p3=1` 表示整段 256 B，`p3=0` 时 `p4` = 尾段长度 | 从缓冲流式送出 `len = (p3<<8)|p4` 字节给屏 |
| `0x0A` | `DRAW_DIRECTION`：`p3 = 0/1` | 设显示方向并重新初始化屏 |
| `0x00`–`0x06`、`0x09`、`0x0B` | 官方上位机未使用 | 固件内建绘图指令（纯色填充、贴图、单色图、混色图、横线等），用于厂商自有工具 |

### class 0x03 —— 外部 Flash

| sub | 行为 |
|---:|---|
| `0x00` | 按 24 位地址（`p2 p3 p4`）读一页到内存 |
| `0x01` | 按 24 位地址写一页 |
| `0x02` | 擦除地址范围 |
| `0x03` | 写页（第二版实现） |

这些命令对应厂商手册里的 `Erase_Flash_page` / `Write_Flash_Photo_fast` / `Write_Flash_ZK`，官方上位机**没有使用**。

### class 0x04 —— BULK（批量像素）

**不经过 `cmd_dispatch`**，由主循环直接处理：`p1` = 缓冲索引，`p2..p5` = 4 字节像素单元，写入 `tile[idx*4]`。这是刷屏时高频使用的路径，一条帧搬 4 字节。

### class 0x08 —— ADC

| 字段 | 含义 |
|---|---|
| `p1` | ADC 通道号：**9 = 触摸**，**15 = 心跳/电池** |
| 应答 | 6 字节回包：`[0x08, ch, ?, ?, hi, lo]`，采样值 = `(p4<<8)|p5` |

上位机按 `buf[0] == 0x08 and buf[1] == ch` 匹配应答。

## 5. 刷屏流程（上位机实际时序）

一帧 160×80×2 = 25 600 B，按 **256 B 一段**切分，共 100 段：

```
→ 02 00 00 00 00 00          设置坐标 (0,0)
→ 02 01 00 A0 00 50          设置尺寸 (160,80)
→ 02 03 07 00 00 00          进入直写
  ── 每一段重复 ──
→ 02 04 b0 b1 b2 b3          设置本段"最常见 4 字节单元"作为填充
→ 04 idx b0 b1 b2 b3         差异像素，每帧最多 64 条（idx = 0..63）
→ 02 03 08 01 00 00          本段 256 字节发送完毕
  ── 尾段（不足 256 B） ──
→ 02 03 08 00 00 t           发送 t 字节
```

优化逻辑：每段先统计出现次数最多的 4 字节单元作为"填充"，然后只把与该填充不同的单元逐条发下去（阈值 44 条：差异超过 44 条时干脆全发 64 条）。这是典型的手写差分编码——**省带宽，但把复杂度全部推到主机侧**。

## 6. 已知缺陷与兼容性注意

自研固件若要兼容现有上位机，必须复现以下"怪癖"，否则会出现花屏或卡死：

1. **`len == 0` 会卡死**。`0x03` 操作码 `0x08` 的 `len = (p3<<8)|p4` 直接被当成循环次数，主机若发 0，固件进入无限等待。
2. **无任何超时与重传**。单条命令等待 SPI/DMA 完成时是裸轮询，主机异常断开时固件只能靠 5 秒会话超时兜底。
3. **擦除范围用 16 位累加**，`P + N > 0xFFFF` 会回绕，导致擦错区域。
4. **`SET_REPORT` 可写任意 SRAM**：HID 控制传输的 `SET_REPORT` 不带长度/地址校验，`class 0 / sub 0x30 / 子操作 4` 能把主机给的数据写进 `0x20000140 + addr`，`addr` 完全由主机决定——这是个实打实的越界写洞（虽然只能影响 20 KB SRAM）。
5. **无帧校验**。USB 本身保证完整性，因此实际不会出错，但也意味着无法检测协议层错位：一旦丢一个字节，之后所有帧都会错位且不会自愈（只能靠 5 秒超时复位）。
6. **`PA6` 兼作 flash MISO 与屏 D/C**，所以屏幕命令必须与 flash 访问严格串行，中途不能交错——自研固件若改用中断/DMA 并行访问，会直接冲突。
